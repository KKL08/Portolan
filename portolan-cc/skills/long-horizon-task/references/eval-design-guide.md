# Eval 可行性评估指引：判断一个环节能不能自闭环

> 定位：portolan skill 的 reference。预期对齐阶段，agent 对任务的核心环节逐个评估——**能不能给它建出明确的量化闭环 eval**。建得出，这个环节就是可以放心自闭环的部分，eval 本身就是验收；建不出，拆小再试或者标人工点。
> 内容提炼自厂商与评测机构的 eval 设计实践（Anthropic 工程博客、主流长程 benchmark 的设计模式），写成操作指引，不带研究数字。

## 一、判定核心

**一个环节能自闭环 = 能给它建出合格的 eval。** 合格的标准四条：

1. **结果可断言**——完成与否由环境状态或产物判定，不靠 agent 自述
2. **判据独立**——执行者说了不算，也看不见评分逻辑
3. **标准无歧义**——两个内行独立来判，会得出同一个结论
4. **判定可重复**——重跑一遍，结论一致

## 二、评测设计者的思维清单

评估每个环节时逐条过。这是评测行业反复踩坑后沉淀的思维方式：

1. **判结果，不判过程。** 验证终态——数据库里有没有那条记录、测试跑不跑得绿——不规定路径、不检查工具调用顺序。路径检查又脆又罚创造力：agent 常找到设计者没想到的正确做法。

2. **先想参照解。** "如果这个环节做成了，标准产出长什么样？"写得出参照解，说明任务可解、grader 可校验；写不出，往往是规格本身模糊——先回去和用户把预期对清楚，而不是硬写 eval。

3. **两个内行测试。** 这个环节的成败，两个懂行的人独立判会一致吗？会——可以写成断言或 rubric；不会——标准有歧义，歧义写进 eval 就变成指标里的噪声，必须先收敛。

4. **裁判分级，按序选，不可倒置。** 能用机械验证的用机械验证（快、便宜、可重复）：字符串比对、退出码、终态断言、文件校验。机械验证判不了的用质量评审（LLM judge）：rubric 逐维原子化、每个维度独立判、给"不确定"留出口防止硬编。judge 本身要定期和人对表。人工判定放最后，用在校准和主观领域的把关上。（完整四级裁判层级见 `references/architecture.md`「命名约定」节：条件核对 → 机械验证 → 质量评审 → 人工判定；条件核对是 /goal evaluator，不在环节 eval 设计范围内。）

5. **大环节拆 checkpoint，给部分分。** 全对/全错的二元判定掩盖进展和退化。拆成可独立断言的小节点，部分完成可计量——这也正是"拆不出整体 eval 的环节，拆小后往往局部可 eval 化"的原理。

6. **防钻营是设计要求，不是道德期望。** 判据对执行者不可见（评分逻辑暴露必被利用）；产出要防伪造（检查产物来路，不只检查产物存在）；让绕过所有检查比老实做事更费劲。"请不要作弊"的指令没有用。

7. **正反都要测。** 只测"该做的做了"会养出过度执行。配上反向断言："不该改的文件没被改、不该发的没被发、范围外的东西没被碰。"

8. **一次成功和次次成功是两个指标。** 交付型环节看"至少成一次"（失败可以重试，取最好的）；无人值守的重复型环节必须按"次次都成"设计 eval——一个每周自动跑的任务，十次里错一次就是每两个多月炸一回。"次次都成"的操作化：列出边界输入矩阵（空源、超时、格式异常、跨日去重等），每种边界至少一条断言；判定环境固定（时间、外部数据快照），避免随机因素污染判定；试跑阶段"重复稳健性"测项换一组边界输入再跑一遍。

9. **判定环境要稳定。** 时间、外部数据这类随机因素，要么固定住，要么排除出判据，否则判定不可重复，翻车时分不清是任务坏了还是 eval 坏了。

10. **终态断言要配基线。** 只描述终态的判据，分不清"agent 做到的"和"环境本来就是的"。每条正向断言都要配一条"起点时它不成立"的实测记录；反向（约束型）断言相反，起点必须成立。基线等于目标 = 这条判据不成立，回去重定成功标准。

11. **环节 eval 设计成能力阶梯。** 大环节拆成递进小关卡，每关独立断言，过一关记一关。好处：部分完成可计量、退化可定位、试跑时一眼看出能力边界在哪。设计时从最基本的关卡开始，逐级提高难度，每级只加一个新要求。

12. **来路审计意识。** 设计反向断言时多想一步："哪条捷径能绕过终测？"常见的：挖 git 历史抄现成实现、偷看判分脚本与参考解、把别处的产出搬过来冒充自己做的、换措辞重写既有记录冒充新进展。这类约束写进任务协议单反向断言，finish 时靠 journal 证据指针与产物来路审计。

13. **跨边界要配跨边界断言。** 环节改动跨越包/服务/系统边界时（本仓库改完、消费方在别处），仓库内的测试网天然只到边界为止，断裂完全隐形。为这类环节在验收清单额外配一条可跑的跨边界断言——一行命令加一个预期值，验证边界另一侧消费方的语义，不只挂本仓库测试结果。

## 三、评估流程

对基础摸底评估阶段拆出的每个核心环节：

0. **规格留白扫描**（起草前先做一遍）：任务规格是外部给定的（issue、instruction、需求文档）
   时，不要把规格**整体**概括成参照解就算数——逐个接口/判定追问"它在边界情况下的行为，
   规格说了吗"，把每个返回值与判定的边界情况列成表，标出规格未定义的格子：

   | 接口/判定 | 边界情况 | 规格是否定义 | 处理方式 |
   |---|---|---|---|
   | {{接口名}} | {{空输入 / 非典型状态 / 未知标识}} | 未定义 | 靠失败反馈反推 / 问用户 / 标人工确认点 |

   有留白 → 写进任务协议单成功画像下方的"已知规格留白"小节。执行环开工就知道哪几处得靠
   失败反馈反推，而不是撞上去才发现；finish 也能据此判断"反推得对不对"是否该升级为
   人工确认点。留白多到参照解写不出 → 回去和用户对齐预期，别硬写 eval（见第二节第 2 条）。

1. **试写 eval**：按上面的思维清单，给这个环节草拟验收断言 + 参照解
2. **按结果分流**：
   - **写得出硬 eval**（代码可判）→ 自闭环候选，eval 直接进工作底稿的"环节与证明清单"
   - **写得出软 eval**（rubric + 不弱于执行者的 judge）→ 自闭环候选，但标注 judge 校准点，人定期抽读
   - **写不出** → 先拆小再试；拆不动，标人工点
3. **产出"可自闭环比例"图景**：任务里多大比例的环节有 eval 兜底，直接呈现给用户——"这个任务能放多手"的答案由当场建出来的 eval 说话，不查任何先验评级表
4. **如实交底**：写不出 eval 又拆不动的部分，明说"这段没法自动验——要么你来把关，要么我们重新定义这段的成功标准"
5. **用户必审四项**：评估产出里的成功画像（参照解）、反向断言、可靠性档位、质量把关节奏，写进任务协议单时必须处在用户定稿会亲眼看到的位置——这四项你推不出真值，只有用户能拍板

## 四、警惕清单

- **基线等于目标的任务是假任务**——起点就满足验收标准，跑完必然"成功"，且证据链每一条都是真的，从产物侧无法识破。只能在发起阶段靠实测基线拦
- **0% 通过率通常是 eval 坏了**，不是 agent 不行——先查任务规格和 grader，再怀疑能力
- **过严的判据会把对的判成错的**——判语义不判字面，格式差异、等价表述不该扣分
- **规格模糊是 eval 写不出的头号原因**——问题多半在第一层没对齐，回去补对齐，别硬写。外部给定的规格尤其要做第三节第 0 步的留白扫描：整体读着完备、逐个边界追问才露馅，是最容易漏的一类模糊
- **eval 自己也要被测**——试跑阶段"裁判判不判得动"那一项，测的就是这里建出来的 eval
