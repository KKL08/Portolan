# 分发组装

> 定位：portolan skill 的 reference。初始化时首次组装执行产物（用确认协议值）；试跑绿灯后按校准值更新并组装 /goal 命令文本；快速通道免试跑直接组装；continue 续跑时重新组装。

## 组装顺序

1. **更新 execution.md**——按 `templates/execution.md`，占位符全部填实：
   - `{{任务名}}`：任务协议单标题
   - `{{熔断值}}`：底稿运行参数（有试跑用校准值，否则用确认协议拍板值；未设则删除停滞自检整段、终态行"无进展"的括注改为"（长期无新证据，自判）"，并在底稿注明）
   - `{{清单，触到必停"需批准"}}`：任务协议单不可逆点原文。续跑时对照批注区审批记录，把已批准条目在 execution.md 显式标注。协议明写"本任务无不可逆动作"的，照填该句并删去其后的批注区审批例外句（/goal 命令中"触到不可逆点停在'需批准'"子句保留，兜协议外突发情况）
   - `{{要点}}`：任务协议单反向断言要点
   - `{{路径}}`：批注区文件路径
   - 首次组装写入任务目录，后续为更新

2. **组装 `/goal` 命令文本**——按下方格式填实

3. **写进底稿分发记录**——命令原文 + 环境准备清单 + execution.md 的冻结哈希（调用 state-guard update-freeze 写入工作底稿"冻结哈希"节；execution.md 是执行者的行为协议，冻结防执行期自改熔断段；续跑重组后重新调用更新此哈希）

4. **打印给用户**——建议在新会话中发射（与 finish 换会话同一逻辑：结构独立靠会话边界，避免执行环带着发起期全部上下文长跑）。打印内容包括：
   - /goal 命令文本
   - 环境准备清单
   - 停下后的下一步："执行结束或停点后，回来运行 `/portolan:continue`（续跑）或 `/portolan:finish`（验收）"

## 冻结哈希

组装完成后，调用 state-guard 更新冻结哈希——除 execution.md / 任务协议单.md /
rubric.md，还要带上任务协议单"评分标准基线"节声明的**评分标准文件**（判分逻辑 +
期望答案，路径相对任务目录，可在任务目录外）：

```bash
state-guard update-freeze --task-dir .portolan/<slug>/ \
    --files execution.md 任务协议单.md rubric.md ../../tests/test_outputs.py
```

冻评分标准是为了让 verify-freeze 自动抓"执行者篡改测试/答案"——被审计者不得动审计
准绳。契约声明本身受契约冻结保护，删声明会被契约哈希抓到，形成闭链。
只冻标准、不冻工作产物（补代码类任务的工作文件本就该变）。

这一步是 finish 第 0 步核对冻结哈希的前提。若 state-guard 未装机，退化为
文本约定（记在决议记录里），但 finish 会因缺少冻结哈希无法机械核对。

## `/goal` 命令格式

> **手动备用模式**：/goal evaluator 只读 transcript、无法编程触发，故作手动备用。本节用于两类场景：① 用户想用宿主原生评估器时手动粘贴到新会话 ② 官方交付可编程 goal 触发后的回归评估。

N 已设时：
```
/goal 按 {{任务目录}}/execution.md 执行任务"{{任务名}}"。完成条件：会话中已声明命名终态（完成/无事可做/被阻塞/需批准/无进展）之一，并给出 journal 证据指针。约束：不得违反任务协议单反向断言（{{要点}}）；触到不可逆点停在"需批准"。or stop after {{N}} turns
```

N 未设时（省略轮次上限子句，打印时提示用户无上限风险）：
```
/goal 按 {{任务目录}}/execution.md 执行任务"{{任务名}}"。完成条件：会话中已声明命名终态（完成/无事可做/被阻塞/需批准/无进展）之一，并给出 journal 证据指针。约束：不得违反任务协议单反向断言（{{要点}}）；触到不可逆点停在"需批准"。
```

### 设计说明

- **停滞自检不写进条件。** evaluator 的语义是"条件满足就判完成"——如果把"连续 N 次无进展则停"写进条件，evaluator 会把熔断判成任务完成。停滞自检写在 execution.md 里由执行者自判。
- **执行中没有质量评审。** 执行者不自派评审 subagent。执行中只有六步节拍里的机械验证。质量判定归 finish。
- **证据必须呈现在对话里。** evaluator 只看对话中已呈现的内容，不会自己跑命令或读文件。执行者声明终态时，证据指针和关键结果要摆在对话里，不能只写进文件。
- **两层卡点关系。** "需批准"是设计内停点（干净收束、journal 有终态声明、continue 可分流）；平台权限门是兜底（权限提示悬置不产生 journal 终态，continue 按"无终态声明"处理）。

## 环境准备清单

组装时一并给出：

- 执行期需要的权限白名单建议（哪些工具/目录需要 allow）
- **不可逆命令绝不建议加白**——平台权限门就是不可逆卡点本体，加白等于拆掉安全网
- 组装时实查现有 allow 规则，若已覆盖协议不可逆命令，提示用户该风险并建议移除
- 提醒执行纪律：journal、协议、证据文件里不落 API key、token 等凭据——任务目录是审计产物，不做脱敏处理

## `/goal` 与 `/loop` 语义附注

以下是官方文档核实的语义，组装时以此为准。平台更新后建议重核此节语义。

**`/goal`**：
- 格式 `/goal <条件文本>`，条件上限 4000 字符
- 每轮结束后 evaluator（小模型）看完整对话判条件是否满足，输出 yes/no + 理由
- 条件满足 → 自动清除 goal，记为完成
- 轮次上限内联在条件文本里：`or stop after N turns`
- evaluator 不执行命令、不读文件——只看对话已呈现内容

**`/loop`**：
- 格式 `/loop [间隔] [提示]`，间隔单位 s/m/h/d（秒会向上取整到分钟）
- 三种模式：间隔+提示 = 定时执行；只有提示 = 动态间隔；只有间隔或空 = 默认维护
- 与 `/goal` 是独立机制：`/goal` 跑到条件满足停，`/loop` 按时间间隔反复跑

## 不可逆环节替身补充

找不到无副作用替身的环节（如对外提 PR——draft PR 也是真实外部动作），试跑只验证到动作前一步（本地建好分支与 commit、组装好标题正文），复盘记"该环节未点火"。可用自己 fork 的仓库当沙箱。
